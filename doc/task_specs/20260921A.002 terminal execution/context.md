# 终端执行器与可靠交易闭环

## 使用场景与设计初衷

无弹窗 CSV 探针证明可以低成本填参和回读，但没有提供业务请求所有权、逐路由准备/复位、执行超时后的隔离及防重发。现有成功键盘交易也仍由独立探针完成，不能直接让多个 HTTP 请求拼接调用这些脚本。

CSV 导入生成未启动记录，重复导入会新增记录，实际发出还需要快捷键。用户接受本地提交后快速返回、再查订单/成交确认；不要求该 HTTP 请求等待柜台回报，也不能用一次仓位没变断定下单失败。影响未知与正常尚未成交需要分开处理。

用户担心快速操作和冲突动作使 GUI 卡死。需要同时解决动作串行、控件就绪等待、超时后的所有权和进程隔离，且不能靠大量固定 sleep 消耗无弹窗 CSV 已取得的性能收益。

交易状态已有按品种和合约直接读取的内部函数，能避免时间规则推算和 GUI 识别；现有探针只证明收盘取数，不能代替状态切换、断线后缓存失效以及正式队列集成。该读取应与其他原生调用共用所有权和生命周期。

## 方案对比

在路由里直接加锁并执行脚本，无法可靠处理 HTTP 取消后底层动作仍运行、Windows 消息调用超时但并未取消等情况。采用独立执行器、持久化阶段和受控 IPC，可明确哪些动作还可能有副作用。

只用相同参数或时间匹配回报会产生歧义；发送前必须确认本地目标，快速观察尚未取得可信柜台订单号时允许为空，不强行认领或等待。纯 CSV 不切页复位，键盘/GUI 通过重复执行无副作用的准备和收尾保证下一请求有明确基线。

## 取舍结论

交易与账户查询保留 CSV → 快捷键 → GUI 优先级，交易状态使用专用原生只读入口；八个业务路由统一排队，执行器独占终端，准备、执行、必要核对和收尾完成后立即交权。共享 CFB 简洁模型在此形成，提交状态与真实订单状态分离；开盘/休盘值来自当前快期品种状态，不使用日历或 GUI 颜色替代。

真实 SimNow 验证只进行有限的一手交易，使用提交和后续查询组合验证，不重复报单制造性能数字。异常先保留详细步骤日志，必要时截图；暂不建立全面异常分类或自动恢复系统，无法确认界面安全时暂停，不能自动换路径重发。
