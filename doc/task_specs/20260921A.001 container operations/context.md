# 容器入口与运行治理

## 使用场景与设计初衷

现有服务通过宿主 Python/uv 脚本构建、启动容器，HTTP 使用标准库服务器及可选 token。用户要求以后只用 just 操作 Podman、应用在容器内运行，且所有 HTTP 路由不做鉴权、默认不发布到公网。

终端及 Wine 输出目前直接追加到固定文件；缺少轮转和总量控制。若直接叠加详细交易日志与每次 CSV 产物，数据会持续增长，甚至因输出收集阻塞或空间不足影响 GUI。需要先建立可独立验证的运行基础，再交给交易执行链路使用。

## 方案对比

保留原服务并另启 FastAPI 会形成双生命周期和两套端口/鉴权逻辑；本阶段直接替换诊断 HTTP 实现。just 若仅包住旧宿主 Python 命令，仍依赖宿主业务环境，因此把配置校验、下载和测试移入容器。

采用容量上限控制日志及工件，按生成顺序淘汰最旧已结束文件，不设置按天或小时到期删除。失败 CSV 与必要截图共用 300 MiB；活动文件和少量防重发依据单独保护，也不能突破相应预算。未知异常先留下诊断事实，不为尚未遇到的情况建立自动修复系统。

## 取舍结论

本阶段交付可构建、可启动、可诊断、可清理的容器基础，不发布交易占位 API，不自动登录账户。配置和诊断契约采用主任务定义，未来执行器复用同一服务与日志基础，避免后续为测试或打包再搭一套链路。
