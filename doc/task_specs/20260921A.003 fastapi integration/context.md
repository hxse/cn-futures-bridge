# 八路由兼容与集成验证

## 使用场景与设计初衷

调用方希望通过已有带鉴权的上层服务转发 CFB，因此八个业务方法、路径后缀和主要输入参数尽量接近参考 CTP 接口；返回由 CFB 自行定义必要信息。CFB 不做鉴权，不负责上层代理实现，也不直接集成 CTP 交易连接。

终端执行器已经定义唯一操作链路，但 HTTP 的参数校验、客户端断开、超时、序列化和日志清理仍可能改变交易语义。集成验收必须证明这些外层行为没有绕过所有权或触发重复副作用。

## 方案对比

原始 CSV 会让调用方理解中文列名，复制 CTP 字段全集又增加大量不可得信息。采用简单 snake_case 模型，把本地提交结果、订单/成交查询和快期原生交易状态分别表达，既减少耦合，也避免把 submitted 误认作成交。品种状态直接给出是否连续交易，未知或失效数据通过错误表达，不以时间规则补值。

另开新服务或路由内直接调用 GUI 会形成第二条交易链路。复用已有 FastAPI 生命周期、共享领域模型和调度器，仅完成 HTTP 绑定，可以把一致性和恢复验证集中到同一实现。

## 取舍结论

业务路由限制为八项且统一排队，诊断与 Swagger 单独保留。提交接口完成本地动作和收尾后返回，由调用方独立查询订单/成交；异常先记录事实并按需截图，不加入复杂自动修复。OpenAPI 说明这种简单契约及 terminal_native 状态来源，不仿造原生柜台回报。

本阶段承接跨模块与双镜像的整体验证，前置已经通过的局部测试由默认离线入口自然覆盖，不重复另建一份验收框架或执行记录文档。
