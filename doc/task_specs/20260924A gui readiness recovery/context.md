# 界面快速检查与恢复

## 使用场景与设计初衷

单账户快期通过唯一 FIFO 接受 API 请求。上一次操作或人工接管留下菜单、资金详情等窗口时，后续快捷键可能作用于错误目标。现有八个路由已有前置检查和 finally 收尾，但多数残留状态直接报错，空标题对话框可能被过滤，检查还会读取完整子控件树。

用户要求每个路由开始前检查并处理可恢复状态，同时遵循高性能、可靠的项目原则。正常界面应快速通过，异常才定向恢复，不让复位增加固定等待或额外业务副作用。

SimNow 全天站点还会出现正文为空的“确认结算单”，状态栏已明确显示查询结算单成功。原规则只接受完整结算正文，会因此持续等待；需为这一明确站点和窗口组合增加限定分支，其他环境仍保留完整正文要求。
## 方案对比

每次强制按 Esc、切页、清空表单会改变本不需要键盘的 CSV 查询，还可能误操作未知确认框。继续只做完整窗口树检查则重复读取许多无关控件，且已知残留无法恢复。

轻量原生摘要可读取主窗口、可见顶层对话框、菜单及输入状态；只有出现具体异常才执行经过身份核对的恢复。完整控件读取仍负责资金、表格和下单板等业务所需数据。

## 取舍结论

复用既有单执行权、通知模板、超时与阻断机制，新增轻量摘要和定向恢复命令。请求前后、空闲检查和 resume 使用同一就绪检查；业务步骤按需读取完整控件。未知窗口、所有权不明及仍在执行的原生调用继续阻断。

下单板保留操作前快照及最终完整回读，跳过已相同的赋值；改变合约后重新读取受影响字段，不复用失效状态。保持 API、配置和交易语义不变。
