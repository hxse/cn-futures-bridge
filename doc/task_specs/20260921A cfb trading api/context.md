# CFB 交易服务与可靠终端执行

## 使用场景与设计初衷

项目通过现有期货交易终端建立中国期货桥接服务，避免调用方直接集成 CTP 登录、采集和协议细节。长期目标包含华安期货，当前开发、调试与在线交易验证仅使用 SimNow。客户端、Wine、字体和桌面均固定版本，两种运行镜像仅 VNC 组件不同。

已有正式代码可以启动终端、提供状态和截图；交易能力仍来自独立调试探针。无弹窗 CSV 导出已取得订单、成交及空持仓/挂单样本；无弹窗导入已验证本地预埋单、字段回读、错误信息、部分成功及重复导入行为。导入并不自动发送，已发送也不代表柜台接受。已有纯键盘成功开平仓证据，不能直接当作 CSV 主链的成交证据。

用户要求将高性能与可靠性作为项目共同基调。第一优先是“CSV 导入参数 → CSV 回读核对 → 快捷键发送 → CSV 读取委托和成交回报”，CSV 均无弹窗；不支持的具体环节使用快捷键，快捷键也不具备能力时才直接操作 GUI。

交易状态采用专用原生读取：用户需要快期实际维护的品种开盘/休盘状态，不接受根据日历、时间表或模拟环境规则推算。固定客户端核心 DLL 提供品种、合约及交易所状态查询，已取得收盘样本；正式服务仍需补齐状态切换与断线恢复验证。

调用方已有另一套服务，期望 CFB 的八个路由与其 `/ctp` 路由保持方法、后缀及主要输入参数相近，只替换为 `/cfb` 前缀；返回不要求兼容 CTP，采用 CFB 自己的必要字段。CFB 无 HTTP 鉴权，默认仅发布到宿主回环地址；上层的鉴权和转发实现不属于本任务。输入参考是 2026-09-21 读取的 `http://127.0.0.1:5123/openapi.json`，服务标题 `ccxt-proxy2`、版本 `1.0.0`；必要内容已经转写进本任务扩展，实施不依赖该服务持续可用。

一个账户仍可能接收并发 HTTP 请求。CSV、键盘、资金窗口和查询都访问同一 GUI；仅增加 sleep 不能阻止操作互相穿插。HTTP 超时也不能证明已取消实际操作。执行所有权、等待条件、结果关联和持久化记录需要共同设计。

用户接受提交与结果确认分步进行：下单或撤单完成本地提交和界面收尾后返回，由调用方查询订单、成交和持仓确认结果。只看持仓无法区分拒单、挂单未成交与数据尚未更新，不作为单笔委托成功判据。

用户需要每一步可追踪的日志，截图只在确有诊断价值时生成；现阶段不预测全部异常并建立复杂自动修复。日志和工件只按容量清理，失败 CSV 与截图共用 300 MiB 上限。运行和测试均在 Podman 容器中进行，宿主通过 just 一行构建、启动，不能要求在宿主部署 Python 业务环境。

## 方案对比

| 选择 | 收益 | 限制 |
| --- | --- | --- |
| 无弹窗 CSV 填参与读取，快捷键发送 | 复用终端校验，减少逐字段输入和弹窗，已有可重复样本 | 导入可能部分成功或重复，发送前仍须核对本地目标 |
| 全程快捷键 | 部分交易行为已有真实模拟成交 | 填参步骤较多，仍受页面与焦点影响，表格读取能力有限 |
| 进程内原生状态查询 | 可按品种/合约直接取值，不改变页面或生成文件 | 非公开接口，必须锁定版本并确认会话与数据有效性 |
| 直接 GUI 操作 | 可补充资金读取、局部状态或其他缺失环节 | 定位及恢复更复杂，只作为具体能力的后备方式 |
| 每个 HTTP 请求自行操作 GUI | 表面实现简单 | 无法维护全局操作顺序，超时后也容易产生重复发送 |
| 单执行器与有界队列 | 明确所有权，可隔离阻塞，统一去重与错误处理 | 必须区分排队、执行和发送后等待，不能仅包一层线程锁 |

复制完整 CTP 返回结构会引入终端无法提供的大量字段，因此只保留调用方判断委托、成交、持仓和资金所需的信息。交易状态直接读取已登录快期进程中的品种状态；日历只能回答计划时段，交易所指示又不能准确代表每个品种，因此均不作为业务来源。二值结果只表示是否连续交易，不能保证账户权限或委托接受。

统一盲按 Esc 不能把任意窗口变成安全基线。纯 CSV 不改变页面时无需切页复位；键盘和 GUI 路径采用可重复的准备及收尾步骤，退出自己打开的已知窗口后再交出执行权。

## 取舍结论

采用一个主任务、三个有独立验证边界的实施阶段：先建立容器入口及可控的日志基础，再实现终端执行与恢复，最后接入业务路由并完成整体验证。各阶段沿同一正式链路推进，不维护旧 HTTP 服务与新服务两套实现。

路由和主要输入尽量兼容参考，输出采用简洁的 CFB 模型；提交接口不循环等待柜台回报，查询接口承担后续确认。原生市价、IOC/FOK 等输入业务含义继续逐项验证，不能因输出简化而将它们替换为近似行为。

正常流程减少不必要的界面切换、进程启动和等待；异常先记录事实、按需截图、返回明确状态，界面无法确认安全时暂停，不自动补单或猜测性修复。轻量防重发记录与可淘汰的诊断文件分开，不把正常等待用户查成交的 submitted 状态当作系统故障。
